# Oh my god — Evidence Rule

Любое утверждение о соответствии, работе, статусе или качестве — НЕДОКАЗАНО, пока нет
воспроизводимого артефакта. Артефакт = файл в репозитории (например
`verification/<дата>-<чек>.txt`), который можно перезапустить и получить тот же результат.
Утверждение без артефакта считается НЕДОКАЗАННЫМ, а не «PASS по смыслу».

## Три состояния ответа

| Состояние | Условие | Действие |
|-----------|---------|----------|
| **ДОКАЗАНО** | Есть сохранённый артефакт (вывод команды, лог, ps, запрос, diff), воспроизводимый тем же запуском | Фиксировать артефакт, ссылаться на него |
| **НЕДОКАЗАНО** | Артефакта нет, проверка не доведена до конца, результат не воспроизведён | Зафиксировать как открытый долг, задать вопрос пользователю. НЕ маскировать «частично»/«PASS с замечаниями» |
| **НАРУШЕНО** | Доказан факт несоответствия | Чинить КОД/реализацию, а не требование. Требование меняется только по явному решению пользователя |

## Workflow (обязательные шаги)

1. **Собери требования.** Выпиши инварианты/чек-лист из задачи дословно. Не пересказывай своими словами.
2. **Спланируй доказательства.** Для каждого пункта — какая команда/проверка даст артефакт, куда он ляжет (`verification/<дата>-<чек>.txt`).
3. **Исполняй буквально.** Команды проверки из требований — как написано. Кривая команда = дефект команды (фиксируется отдельно), но требование всё равно доказывается вручную до конца.
4. **Снимай артефакты ДО остановки.** `ps`, логи, живые запросы — до `down`. Закрытие стека без артефактов = рантайм не доказан.
5. **Пиши event log.** Каждая проверка — append-only JSON-строка в журнал (см. ниже).
6. **Проведи независимый judge.** Повторно проверь каждый критерий свежим контекстом, включая ранее PASS (регрессии).
7. **Закрой Goal Closure.** Ровно одно из 4 состояний (см. таблицу). Для C-уверенности полное завершение запрещено.
8. **Stop-hook.** Не завершай сессию/стек, пока не пройдены обязательные проверки (typecheck, test, lint) и не сняты все артефакты.
9. **Скрипт поиска или анализа (если создан).** Сначала загрузить скилл `analysis-script-rules` и пройти его самопроверку. Артефакт `verification/<дата>-self-test.txt`.

## 7 правил Evidence Rule

### 1. Артефакт вместо слова
Цифры, статусы, «healthy» — только с файлом-доказательством в репозитории.
Нет файла → нет результата. Артефакт должен содержать: команду, вывод, дату, окружение.

### 2. Два состояния, не «частично»
Если не проверил до конца — это НЕДОКАЗАНО. Фиксируется как открытый долг, НЕ маскируется.
Запрещены формулировки «частично», «PASS с замечаниями», «зачту по смыслу».

### 3. Сквозная трассировка факта
Любой факт (порт, имя, значение) прослеживается по ВСЕЙ цепочке:
источник → конфиг → клиентские ссылки → связанные конфиги → документация.
Не останавливаться на первом вхождении. Каждый затронутый baseline/ADR/контракт
фиксируется как `preserved | rebound | retired | rejected` (Baseline alignment).

### 3.1. Сквозная трассировка реализации (процесса)
Проверка наличия инструкции/шага ≠ проверка работоспособности. Трассировать ВСЮ
цепочку реализации до конечного артефакта: инструкция → вопрос → ответ → действие →
результат. Обрыв цепочки (вопрос задан, но ответ не используется; правило написано,
но не применяется) = НЕДОКАЗАНО. Для субагентов: реально запустить и проверить, с какой
моделью/параметрами запустился. Для процессных правил: применить и проверить, что
новое поведение сработало (а не просто «файл изменён»).

### 3.2. Верификация пар consumer-producer (метрики, дашборды, API)
Статическая проверка файлов не ловит расхождение имён/схем между потребителем и
производителем. Для связок exporter→dashboard, API→клиент, схема→миграция: запросить
реальные данные у производителя (curl /metrics, API endpoint, БД) и сверить каждое
имя/поле, которое использует потребитель. Особое внимание: суффиксы (_total, _count),
версии экспортёров, регистр. Несовпадение = НАРУШЕНО, даже если оба файла «существуют
и синтаксически корректны».

### 3.3. Верификация точек связывания (binding points): конфиг vs рантайм
Каждая точка связывания двух компонентов проверяется в рантайме, а не статически.
Паттерн: «конфигурация предполагает X, но реальное поведение — Y». Типичные случаи:
(а) volume mount — конфиг монтирует путь X, но приложение пишет в Y (проверить:
docker exec + ls, документация образа); (б) metric names — дашборд ссылается на имя X,
экспортёр публикует Y (проверить: curl /metrics); (c) API paths — клиент вызывает /v1/X,
сервер слушает /v2/Y (проверить: curl эндпоинта); (d) config keys — приложение читает
KEY_X, а в .env лежит KEY_Y (проверить: документация/strace). Общее правило: не доверять
имени файла/переменной/пути — проверить, что компонент реально использует именно его.

### 4. Код приводим к требованию
Требование меняется ТОЛЬКО по явному решению пользователя, с обоснованием и фиксацией.
Никогда не «переписывать инвариант под реализацию» молча. Несоответствие → чинится код.

### 5. Рантайм доказывается артефактами ДО остановки стека
`ps`, логи, живые запросы снимаются и сохраняются до `down`. Закрытие стека без
артефактов = рантайм не доказан. Сначала артефакты, потом остановка.

### 6. Команды проверки из требований исполнять буквально
Кривая команда = дефект команды (фиксируется отдельно), но требование всё равно
доказывается вручную до конца. Кривая команда не даёт права на PASS.

### 7. Каждое «НЕДОКАЗАНО» → открытый вопрос пользователю
Не молчаливый «зачту по смыслу». Формат вопроса: что не доказано, что сделано,
что нужно для закрытия.

### 8–10. Скрипты поиска и анализа
Правила вынесены в скилл `analysis-script-rules`. Загрузить его перед записью или правкой такого скрипта.

## 11. Мини-тест перед выдачей правки
Любая правка кода, скрипта, конфига, regex: до кода выписать варианты входа, включая edge-кейсы.
Прогнать правку на маленьком примере у себя, сравнить вывод с ожиданием. Не совпало — чинить и прогнать снова.
Отдавать только с выводом прогона; тест-кейсы сохранить в артефакте.

## Усиление (полная проверка, разделение автор/ревьювер)

Применяется ко ЛЮБОЙ проверке соответствия и ревью. Эти пункты предотвращают
«ДОКАЗАНО по смыслу» при неполной проверке.

1. **«ДОКАЗАНО» только при ПОЛНОЙ проверке.** Неполная проверка (часть источников,
   часть критериев) = НЕДОКАЗАНО + вопрос пользователю. «PASS/зачту по смыслу» запрещён.
2. **Артефакт доказывает ИМЕННО заявленное утверждение.** Проверка «список сервисов
   верен» ≠ «все связи верны по направлению». Если утверждение шире проверки —
   это НЕДОКАЗАНО, а не PASS.
3. **Проверка связей включает смысл и направление, а не только наличие.**
   Для диаграмм/конфигов: полнота (каждая реальная связь отражена) + направление
   (источник→цель) + запрет фантомных стрелок + подписи по типу связи.
   Для диаграмм проекта это исполняет скрипт `python3 infrastructure/scripts/check-diagram.py`
   (инвариант 7.11). Для других проектов — аналогичная сверка с конфигами.
4. **Ревью отдельным проверяющим.** Правка диаграмм/структур/конфигов — обязательный
   ревью-проход независимым субагентом-ревьювером на ОТДЕЛЬНОЙ модели (автор ≠ проверяющий).
   Модель ревьювера ВЫБИРАЕТСЯ пользователем при старте КАЖДОЙ задачи (глобальный AGENTS.md,
   «Процессное правило»), а не фиксируется навсегда в `reviewer.md`. В момент ревью используется
   выбранная модель (целевой агент `reviewer-go-*` с зафиксированным `model:` в frontmatter,
   либо явное указание модели для этой сессии). Ревьювер читает файлы (read/glob/grep),
   не редактирует.

## Шаблон артефакт-файла

Файл: `verification/<дата>-<чек>.txt` (дата `YYYY-MM-DD`).

```
ЧЕК: <название проверки>
ДАТА: <YYYY-MM-DD HH:MM>
ТРЕБОВАНИЕ: <дословно из задачи>
КОМАНДА: <как исполнена, буквально>
EXIT STATUS: <0/1/...>
ВЫВОД:
<полный вывод команды>
ПОКРЫТАЯ ОБЛАСТЬ: <что проверено>
НЕПОКРЫТАЯ ОБЛАСТЬ: <что осталось>
ОСТАТОЧНЫЙ РИСК: <что может сломаться>
УВЕРЕННОСТЬ: <A | B | C>
```

## Evidence Slots (для любого утверждения о завершении)

| Слот | Содержание |
|------|-----------|
| Действие/проверка | Что именно выполнено (команда, шаг) |
| Exit status | Код возврата/результат |
| Покрытая область | Что проверено |
| Непокрытая область | Что не проверено |
| Остаточный риск | Что может сломаться |
| Градация уверенности | A / B / C |

Градация уверенности:
- **A** — цель + регрессии пройдены, неизвестного нет.
- **B** — ограниченный остаточный риск (задокументирован).
- **C** — частично. Для C полное завершение ЗАПРЕЩЕНО — только открытый долг + вопрос.

## Goal Closure (ровно 4 состояния)

| Состояние | Условие |
|-----------|---------|
| `done` | Все критерии ДОКАЗАНО артефактами, уверенность A |
| `blocked` | Внешняя зависимость/препятствие, не зависящее от исполнителя |
| `needs-verification` | Есть недоказанные критерии или устаревшие доказательства |
| `scope-exceeded` | Работа вышла за рамки задачи |

Понижение статуса при частичных/устаревших доказательствах: если доказательства
устарели (репозиторий изменился) или частичны — статус понижается до
`needs-verification`, а не остаётся `done`.

## Stop-hook

Не завершать сессию/стек, пока:
- [ ] Обязательные проверки пройдены (typecheck, test, lint — какие применимы)
- [ ] Все артефакты сняты и сохранены в `verification/`
- [ ] Event log дописан
- [ ] Независимый judge выполнен (включая регрессии ранее PASS)
- [ ] Goal Closure выставлен (не `needs-verification` без открытого вопроса)
- [ ] **Если создан инструмент анализа:** самопроверка по скиллу `analysis-script-rules` пройдена, артефакт `verification/<дата>-self-test.txt` создан

## Независимый judge

Повторная проверка каждого критерия свежим контекстом, включая ранее PASS (регрессии).
Judge не доверяет предыдущим выводам: перезапускает команды или сверяет артефакты
с текущим состоянием репозитория. Результат judge — в event log.

Judge выполняется в ОТДЕЛЬНОМ контексте (новый запрос/сессия), а не в том же. Тот же контекст — повторение своих же галлюцинаций. Свежий контекст не знает предыдущих выводов и доверяет только артефактам.

## Event log (append-only)

Журнал проверок в `verification/event-log.jsonl`. Каждая проверка — одна JSON-строка,
дописывается в конец, ничего не перезаписывается:

```json
{"ts":"2026-09-13T10:00:00Z","check":"<имя>","command":"<команда>","exit":0,"state":"ДОКАЗАНО|НЕДОКАЗАНО|НАРУШЕНО","confidence":"A|B|C","artifact":"verification/2026-09-13-<чек>.txt"}
```

## Baseline alignment

Каждый затронутый baseline/ADR/контракт фиксируется в отчёте одним из статусов:
- `preserved` — не менялся, подтверждён
- `rebound` — возвращён к исходному после отклонения
- `retired` — выведен из эксплуатации (по решению пользователя)
- `rejected` — отклонён (по решению пользователя)

## Границы

- Не выдавать красивые отчёты вместо результатов. Лучше честное «не доказал, вот что
  сделаю», чем ложное «всё ок».
- При неуверенности/неполном доказательстве писать «НЕДОКАЗАНО» и спрашивать.
- Требование меняется только по явному решению пользователя — с обоснованием и фиксацией.

## Уроки после задачи (по запросу)

- Источник: текущая сессия.
- Урок — своя ошибка или поправка пользователя. Годится для любого проекта и задачи.
- Цель урока: меньше итераций, токенов и времени до результата, который устроит пользователя.
- Урок уже был — не дублировать. Сделать хук на него и подключить.
- Сохранять в память, которая есть в этой среде. Ответ — caveman ultra, по-русски.

## Режим ответов — caveman full (русский)

Отвечать в режиме caveman full: короткие фразы, без воды, без артиклей, фрагменты
допустимы, технические термины и код — без изменений.

Стиль: предложения до 10–12 слов, простые слова, технические термины не упрощать, отрицания сохранять.

Граница: код, коммиты, документы, тикеты и память пишутся обычной прозой, не caveman.

Auto-Clarity — когда ОТКЛЮЧИТЬ caveman (говорить полным текстом):
- Предупреждения о безопасности.
- Подтверждение необратимых действий.
- Многошаговые последовательности, где пропуск союза ломает порядок.
- Сжатие создаёт техническую неоднозначность.
- Пользователь просит уточнить или повторяет вопрос.

После ясного участка — вернуться к caveman.
