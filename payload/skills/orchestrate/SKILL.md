# Оркестратор задачи

## Когда применять
Да — задача на несколько шагов и компонентов, где ошибка дорогая и нужна независимая проверка:
реализация модуля или фичи после одобрения дизайна; изменение контрактов (схемы, темы, API, миграции);
рефакторинг через несколько модулей; дизайн модуля, который пойдёт на ревью.
Только фаза 1 (план и ревью линзами, без реализации) — если этап запрещает код (например, дизайн до кода) или нужен только план.
Нет — вопрос, объяснение, правка одного-двух файлов, настройка инструментов, поиск и чтение, баг с понятной причиной: делать напрямую.
Полный прогон — это около 10 агентов; сначала убедись, что задача того стоит.

Цель: качественный результат за минимум раундов и с экономным расходом лимита.
Задача — в аргументах команды. Роли выполняют агенты `orch-*` (у каждого своя модель, effort и только нужные инструменты):

| Роль | Агент | Модель / effort |
|---|---|---|
| План, исследование, эпики | `orch-planner` | Opus / high |
| Ревью плана одной линзой | `orch-lens-reviewer` | Sonnet / high |
| Проверка после реализации | `orch-verifier` | Sonnet / high |
| Ревью соответствия намерению | `orch-intent-reviewer` | Opus / high |
| Судья при замечаниях | `orch-judge` | Opus / xhigh |
| Поиск, выжимки, подготовка контекста | `orch-helper` | Haiku / low |

Реализацию делает текущая сессия. Сложную часть (архитектура, миграции, конкурентность, неочевидный баг) можно отдать агенту `general-purpose` с `model: opus`.
Если агенты `orch-*` не найдены (новые определения подхватываются не сразу) — сообщи пользователю и не подменяй их молча агентом другого типа.

## 0. Перед началом
- Первым делом — уровень задачи по разделу «Когда применять», до любого агента. Сообщи пользователю одной строкой: уровень и почему.
  - «Напрямую» — агентов не запускай, сделай задачу сам и обычным образом.
  - «Только фаза 1» — после плана и ревью остановись.
  - «Полный прогон» — все фазы.
  Если пользователь в команде или в ответе указал уровень сам («всё равно полный прогон», «только план») — следуй его выбору.
- Если в проекте есть `.claude/stage.md` — прочитай. «Не источники» не используются; то, что этап не разрешает (например, код до одобрения дизайна), в реализацию не идёт.
- Заведи журнал прогона в scratchpad: `orchestrate-<дата>.md`. После каждого агента дописывай строку: фаза, агент, токены, вызовы инструментов, время — из уведомления о завершении агента.

## 1. План
1. `orch-planner`: цель и проверяемые критерии готовности, вопросы пользователю, исследование кода, эпики и задачи, границы, риски.
2. Вопросы планировщика — пользователю, до ревью. Без ответов дальше не идти.
3. Ревью плана: параллельно 5 агентов `orch-lens-reviewer`, каждому одна линза:
   - Ценность: решает ли план заявленную проблему, понятен ли результат.
   - Границы: нет ли расползания scope, скрытых зависимостей, нерешённых вопросов.
   - Контракты и данные: API, схемы, БД, события (в Kafka-проектах — Avro-схемы и темы).
   - Риски для прода: миграции, обратная совместимость, откат, наблюдаемость, безопасность — если применимо.
   - Покрытие: все ли шаги и сценарии на месте.
   Дополнительно, только если задача их касается: «Этап» (сверка с `.claude/stage.md`), права и роли, нагрузка, тестовая стратегия, миграция данных, внешние интеграции.
   Каждому передавай только нужное: цель, план, затронутые файлы, известные ограничения.
4. Есть BLOCK или существенный QUESTION — правишь план сам (или `orch-planner`, если правка большая), повторно смотрят только линзы, которые нашли проблему, и только изменённые части.
5. Не больше 3 раундов. Не сошлось — сведи все замечания в один список, `orch-planner` переписывает план с этим списком, дальше без нового полного цикла ревью.
6. План — пользователю на подтверждение перед реализацией.

## 2. Реализация
0. Проверка окружения перед первой правкой — три вызова, вывод в журнал прогона вместе с меткой времени начала реализации (она нужна для пункта 2):

   | Что | POSIX (bash, sh, Git Bash) | PowerShell |
   |---|---|---|
   | Время | `date +"%Y-%m-%d %H:%M:%S%z"` | `Get-Date -Format "yyyy-MM-dd HH:mm:sszzz"` |
   | ОС и пользователь | `uname -a && id` | `[System.Environment]::OSVersion.VersionString; whoami` |
   | Запись, чтение, удаление | `p=".consilium_probe_$$"; echo "CONSILIUM_$$_$(date +%s)" > "$p" && cat "$p" && rm "$p" && test ! -e "$p" && echo "probe removed"` | `$p = ".consilium_probe_$PID"; Set-Content -Path $p -Value "CONSILIUM_${PID}_$([DateTimeOffset]::Now.ToUnixTimeSeconds())"; Get-Content $p; Remove-Item $p; if (-not (Test-Path $p)) { "probe removed" }` |

   Ожидаемо: время, ОС, пользователь, строка `CONSILIUM_…` и `probe removed`. Нет вывода — реализацию не начинать.
1. Параллельно — только задачи, которые не трогают одни и те же файлы, таблицы, API, миграции.
2. После реализации — `orch-verifier`: сборка и тесты, границы задачи, TODO, согласованность, конвенции. Он только проверяет. Передай ему отчёт исполнителя («что сделал и как проверил») и метку времени начала реализации: он сверит каждое заявление с реальными вызовами командой
   `python "$HOME/.claude/skills/orchestrate/tool_calls.py" --cwd "<папка проекта>" --since <метка в UTC, например 2026-10-04T18:00:00Z>`
   (для исполнителя-субагента добавить `--session <id сессии> --agent <id агента>`). Заявление без вызова = НАРУШЕНО (симуляция). Нет проверки окружения из пункта 0 — тоже НАРУШЕНО.
3. Затем параллельно два ревью:
   - техническое — `orch-lens-reviewer` с линзой «тесты проверяют поведение, ошибки и граничные случаи, авторизация и валидация, утечки, транзакции и идемпотентность»;
   - по намерению — `orch-intent-reviewer`.
4. Есть замечания — `orch-judge`: реально ли, чинить сейчас / отдельная задача / отклонить, минимальный список исправлений. У судьи только чтение: выполни ту же команду `tool_calls.py` сам и передай ему её вывод, чтобы он проверял заявления исполнителя и ревьюеров по факту вызовов.
5. Исправляет тот же исполнитель. После правки повторная проверка только затронутых мест.
6. Не больше 3 раундов. Не сошлось — нерешённые замечания одним списком, доработка (сложная часть — Opus), затем одна финальная проверка `orch-verifier`.

## 3. Эскалация пользователю
Продуктовое решение, конфликт требований, пробел в требованиях, необратимый шаг, нехватка контекста — не решай сам. Пользователю: вопрос, варианты, рекомендация, последствия каждого варианта.

## 4. Экономия лимита
- Полный набор ревью не повторять, если изменилась одна часть.
- Opus не тратить на простые задачи; xhigh — только судья.
- Агентам — только нужный контекст, не весь разговор.
- Лимит на исходе или Opus недоступен: план и судья — Sonnet / high, механика — Sonnet / medium, вспомогательное — Haiku / low. Сказать пользователю, что идёт упрощённый режим.

## 5. Итог
Пользователю: что сделано, вердикты ревью и судьи, что осталось открытым, журнал расхода по фазам (сумма токенов и времени).
